Building reliable Telegram bots with grammY.js

Author Amin Farahani
Published October 6, 2026
Reading time 5 min read

Getting a Telegram bot to answer /start takes ten minutes. Keeping it answering for months — through traffic spikes, API errors, restarts and payment callbacks — is the real work. After building more than ten bots for automation, API-driven workflows and crypto payments, these are the habits I now apply to every project built with grammY.

1. Long polling for development, webhooks for production

Long polling (bot.start()) is perfect on a laptop: no public URL, no TLS. In production I switch to webhooks — Telegram pushes each update to an HTTPS endpoint, so the bot only works when there is something to do and scales behind a normal web server.

import express from "express";
import { Bot, webhookCallback } from "grammy";

const bot = new Bot(process.env.BOT_TOKEN);
bot.command("start", (ctx) => ctx.reply("Hi! How can I help?"));

const app = express();
app.use(express.json());
app.post("/telegram", webhookCallback(bot, "express", {
  secretToken: process.env.WEBHOOK_SECRET, // rejects requests not sent by Telegram
}));
app.listen(3000);

Register the URL once, with the same secret, so Telegram signs every request:

await bot.api.setWebhook("https://bot.example.com/telegram", {
  secret_token: process.env.WEBHOOK_SECRET,
});

Answer webhook requests quickly. If a handler needs to call a slow API or generate a report, acknowledge the user first and move the heavy part to a queue or background job.

2. Respect rate limits — and let the library retry

Telegram throttles bots: roughly one message per second in a single chat, about twenty per minute in a group, and around thirty per second overall when broadcasting. When you exceed them the API returns 429 Too Many Requests with a retry_after value. Instead of handling that by hand everywhere, install the auto-retry plugin once:

import { autoRetry } from "@grammyjs/auto-retry";

bot.api.config.use(autoRetry());

For broadcasts to thousands of users, also pace the sending itself (a simple queue or grammY's throttler plugin) so retries stay the exception, not the rule.

3. One place for errors

An unhandled exception in one handler should never take the whole bot down. With long polling, bot.catch is the single place to log and classify errors:

import { GrammyError, HttpError } from "grammy";

bot.catch((err) => {
  const e = err.error;
  if (e instanceof GrammyError) {
    console.error("Telegram rejected a request:", e.description);
  } else if (e instanceof HttpError) {
    console.error("Could not reach Telegram:", e);
  } else {
    console.error("Bug in a handler:", e);
  }
});

Behind a webhook, errors bubble up to your web framework instead — wrap your handlers with bot.errorBoundary() so the same logic applies in both modes.

4. State that survives a restart

grammY's sessions keep per-chat data, but the default storage lives in memory and disappears on every deploy. For anything that matters — a multi-step form, a cart, an onboarding step — use a persistent storage adapter such as Redis:

import { session } from "grammy";
import { RedisAdapter } from "@grammyjs/storage-redis";

bot.use(session({
  initial: () => ({ step: "idle", cart: [] }),
  storage: new RedisAdapter({ instance: redis }),
}));

For longer dialogues, the conversations plugin lets you write the flow as straight-line code (await conversation.wait()) instead of a hand-made state machine.

5. Make payments and callbacks idempotent

Payment confirmations — from a gateway webhook or a blockchain watcher — can arrive twice, late, or out of order, and Telegram may redeliver an update after a timeout. Treat every external event as "maybe a duplicate":

  • Store a unique key for each event (transaction hash, invoice id, update_id) with a database unique constraint.
  • Credit the user only inside the same transaction that inserts that key.
  • Always call ctx.answerCallbackQuery() so the button stops spinning, even when the action is rejected.

6. Deploy it like a service, not a script

  • Run it in Docker with a restart policy and a /health endpoint.
  • Keep the bot token and secrets in environment variables — and rotate the token in BotFather if it ever leaks.
  • Log every failed API call with the chat id and handler name, so a user report can be traced in seconds.
  • Put Cloudflare (or any reverse proxy) in front of the webhook and keep the origin closed to everything else.
Takeaway: most bot outages are not clever bugs — they are missing retries, lost sessions and duplicated callbacks. Decide how each of those is handled before the first user arrives.
